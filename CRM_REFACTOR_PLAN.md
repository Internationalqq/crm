## Как использовать GPT-6 Astra для этой работы

Проверено [официальное руководство OpenAI по GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model). Оно рекомендует явно задавать границы задачи, ожидаемую самостоятельность, правила работы с инструкциями и соразмерную проверку результата.

Для этой CRM рабочая схема такая: конкретный сценарий → воспроизведение → небольшой законченный набор изменений → тесты затронутой логики → браузерная проверка → обновление плана. Существенные решения фиксируем в репозитории. Изменения требований можно давать прямо по ходу работы. Большие функции разделяем после фиксации текущего поведения тестами. Название модели здесь — GPT-6 Astra; к frontend-фреймворку Astro это отношения не имеет.

Дополнение от 12 сентября: изучены публичные отчёты о применении Astra. [Порядок работы с Medium/High](ASTRA_CRM_WORKFLOW.md) содержит источники, выбор режима по этапам, критерии проверки и готовые задания. Постоянные правила закреплены в [AGENTS.md](AGENTS.md). Для понятных локальных изменений рекомендуем Medium; для связанных состояний, доступа, финансов и миграций — High. Это рекомендация для проекта, а не результат собственного сравнительного теста режимов.

## Дизайн: обязательная программа

### Общие правила

- Спокойный светлый фон, белые рабочие поверхности, один синий акцент. Зелёный — завершение, оранжевый — внимание, красный — ошибка или блокер.
- Использовать существующие токены отступов `4 / 8 / 12 / 16 / 24 / 32 px`. Страница: 24 px на компьютере, 16 px на телефоне. Карточка: 16–24 px. Между связанными полями: 12–16 px.
- Основной текст 14–16 px; подписи 12–13 px; заголовок страницы 24–28 px. Убрать чрезмерную жирность и прописные буквы у второстепенных подписей.
- Одна главная кнопка на рабочий блок. Редкие действия — в меню. У кнопок с одной иконкой есть доступное название.
- Единые высоты полей, кнопок и строк. Удобная зона касания для действий на телефоне — целевой размер 44 px.
- В таблицах числа выровнены вправо; единица измерения рядом с количеством; заголовок закреплён; длинные названия читаются без потери смысла.
- Выполненные работы не перечёркивать целиком: статус и прогресс уже передают завершение, а название нужно читать при сверке.
- Тени оставить для всплывающих слоёв. У обычных блоков достаточно границы и пространства. Не добавлять очередной `final-fix.css` поверх прежних исправлений.
- Настоящие фото объекта и отчёта сохраняют ценность. В рабочем списке полезнее компактная обложка или строка; большой фотоблок уместен в обзоре объекта и публичном портфолио.

### Изменения по экранам

| Экран | Целевое поведение | Проверка готовности |

| Панель | Компактный заголовок, ключевые показатели, приоритетные действия, рабочие объекты | Без прокрутки видны показатели и начало списка; нет ложных нулей вместо отсутствующих данных |

| Документы | Фильтры по типу и статусу, быстрый просмотр, связанные операции | Из документа можно перейти к объекту и основанию его появления |

| Публичный просмотр | Опубликованные отчёты и график без внутренних элементов управления | В DOM и API отсутствуют запрещённые финансовые поля и неопубликованные материалы |

### Как привести CSS в порядок

1. Зафиксировать снимки ключевых экранов и основных состояний: пусто, загрузка, ошибка, длинные названия, заполненная таблица, диалог.
2. Оставить один источник токенов — `tokens.css`.
3. Ввести владельцев компонентов: оболочка, кнопка, поле, карточка, таблица, вкладки, диалог, уведомление. Использовать их на новых и мигрируемых экранах.
4. По одному компоненту переносить правила из `overrides.css`, `ui-system.css`, `ui-final.css`, `ui-qa.css` и более поздних дополнений. Заменённые правила удалять в том же изменении.
5. Исправлять специфичность и порядок подключения. Изменение всех `!important` за один раз слишком непредсказуемо.
6. Проверять 390, 768 и 1280 px, клавиатуру, фокус после закрытия формы и режим уменьшенного движения. Это критерии следующих итераций; все эти комбинации пока не проверены.

## Backend и frontend-логика

### Разделение ответственности

Целевая структура: HTTP-обработчик → проверенная команда → доменная операция → запросы к БД → сериализация ответа. Общие функции времени, денег, количества, аудита и доступа должны иметь одного владельца.

| Текущий узел | Последовательность рефакторинга |
|---|---|
| `backend/server.py` | Сначала вынести миграции; затем таблицу маршрутов и отдельные обработчики задач, панели и интеграции. Существующие URL сохранить |
| `backend/schedule_tasks.py` | Разделить чтение графика, расчёт, редактирование операций, календарные правила и снабжение |
| `backend/communications_docs.py` | Разделить документы, дневные отчёты, фото, уведомления и чаты; операция сохранения отчёта остаётся атомарной |
| `backend/economics.py` | Выделить базу, обязательства, фактические затраты, платежное разнесение и прогноз; сохранить ограничения БД |
| `backend/finance.py` | Отделить денежные события от чтения файлов и извлечения реквизитов |
| `backend/warehouse.py` и `schedule_tasks.py` | Свести повторяющиеся материальные сводки к одному расчёту с разными представлениями |
| `frontend/assets/js/app.js` | Отделить панель, список/карточку объекта, документы, профиль, уведомления; убрать цепочки переопределения функций |
| `planning.js`, `operations.js` | Выделить график, реестр работ, форму отчёта, смены и медиа в самостоятельные модули |
| `core.js`, `router.js` | Явные `mount/unmount`, снятие обработчиков и таймеров; отмена запросов и правила инвалидирования кеша |

Смена фреймворка или БД не является обязательным первым этапом. Текущая архитектура позволяет начать с выделения модулей и проверки поведения.

### Правила данных и операций

- Общий справочник статусов для хранения, API и интерфейса. Перевод старых значений при чтении уже добавлен; отдельная миграция хранения потребует карты всех существующих значений.
- Единое бизнес-время. Начатое исправление охватывает прежние `TODAY_ISO`; далее согласовать остальные `date.today()` и frontend-дату в долго открытой вкладке с датой сервера.
- Стабильные ссылки между сметой, предложением, заказом, поставкой, документом, движением склада, фактом и оплатой.
- Деньги — копейки и явный режим НДС. Количества — нормализованная единица плюс исходное значение. Эвристику «100 м уже умножены» постепенно заменить происхождением импорта и явным коэффициентом.
- Команды записи с ключом повторного запроса. Ключ сохраняется при повторе после сетевой ошибки; сервер возвращает прежний результат, а не создаёт вторую операцию.
- Для одновременного редактирования — номер версии записи и понятный ответ о конфликте. Пользователь видит, что изменил коллега.
- Для длительных заданий — сохраняемые статусы, число попыток, срок следующей попытки, таймаут, причина ошибки. Уже имеющийся кеш рынка не заменяет очередь финансовых документов.
- В миграциях — номер версии, предусловия и отчёт. Проверка восстановления резервной копии должна включать SQLite и файлы документов.
- Завершить переход со старых `budget/paid/spent` по правилам `PROJECT_ECONOMICS_SPEC.md`; не смешивать старые агрегаты с новой утверждённой экономикой.

## Что перенять из задачи про 101 и «Створку»

Исследование полезно как конкретный список рабочих сценариев. Часть предложенного уже имеет фундамент в этой CRM: версии смет, происхождение данных, обязательства, разнесение платежей, складское сторно и согласование экономики. Их нужно расширять.

| Инициатива | Что добавить здесь | Приёмочный сценарий |
|---|---|---|
| **Входящие чеки** | Сохранение оригинала сразу, стабильный ID, QR/OCR/ручной черновик, статусы распознавания | Провайдер недоступен: документ остаётся доступен и повторно обрабатывается |
| Защита от дублей | Фискальная идентичность, хеш файла и идентификатор входящего сообщения; совпадения проверяются в доступном контуре | Один документ пришёл из CRM и Telegram: расход создан один раз |
| Происхождение строки | Исходная строка, нормализация, источник, исправления человека, связи с фактом | Из расхода открывается исходный документ и история изменения строки |

| Контекст цены | Регион, упаковка, единица, НДС, доставка, наличие, время и источник | «Дешевле» сравнивается на одинаковую физическую единицу и включает доставку |

| Telegram | Принять чек/фото/голос, показать статус, создать черновик, открыть сложную форму | Повторная доставка сообщения не удваивает запись; данные доступны и через CRM |
| AI-действия | Проверяемый черновик с последствиями и подтверждением в рамках прав пользователя | До проведения видно изменение суммы, количества и затрагиваемого объекта |
| Кабинет заказчика | Разрешённые факты, фото, документы, согласования и история | Внутренняя себестоимость не попадает в клиентское представление |

Для чеков достаточно начать с `receipt_documents`, `receipt_lines`, `receipt_allocations`, `recognition_attempts` и ссылок на существующие документы/экономические события. Точные названия и схема согласуются с текущими таблицами при реализации; это проектное предложение, не уже существующие таблицы.

Первый выпуск приёма чеков может работать с оригиналами и ручной проверкой строк. Подключение внешнего распознавателя — следующий адаптер. Финансовое проведение разрешается только после проверки реквизитов, суммы и распределения.

## Полезные добавления сверх исследования

1. **Единая очередь решений руководителя.** Неподтверждённые расходы, перерасход, поставка без документа, работа с блокером и конфликт графика. У каждой записи — причина, ответственный и действие.
2. **Журнал замечаний и дефектов.** Фото → место/работа → ответственный → срок → повторная проверка. Хорошо связывается с уже имеющимися отчётами.
3. **Допработы и изменения сметы.** Запрос изменения → оценка стоимости и срока → согласование → новая версия. Исходная договорённость сохраняется.
4. **Готовность к началу работ.** Материал, люди, техника, документы и предыдущий этап. Система объясняет, почему работа пока не готова к запуску.
5. **Качество данных объекта.** Неназначенные ответственные, отсутствующая компания, неутверждённая финансовая база и несвязанные документы с конкретными переходами к исправлению.
6. **Сохранённые фильтры и быстрый поиск.** Частые представления «мои объекты», «нехватка на неделю», «неоплаченные счета».
7. **Мобильные черновики при плохой связи.** Сначала надёжное сохранение формы и индикатор синхронизации; финансовые действия и изменения остатков подтверждаются сервером.
8. **Обмен с 1С.** После стабилизации идентификаторов и финансовой модели; начать с контролируемого экспорта и сверки результата.
