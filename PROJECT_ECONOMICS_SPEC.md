# Единая экономическая модель объекта

**Версия:** 1.0  
**Статус:** зафиксированная спецификация шагов 1–2; основание для проектирования схемы данных  
**Дата фиксации:** 20 августа 2026 года  
**Область действия:** управленческий учёт объектов CRM; не бухгалтерский и не налоговый учёт

## 1. Подтверждённые решения

1. Управленческие выручка, себестоимость и маржа рассчитываются **без НДС**. НДС хранится и показывается отдельно.
2. Полную экономику объекта пока видят только `main_admin`, `admin` и `director`.
3. `financier` и `accountant` не получают экономические показатели автоматически. Для них позже вводятся отдельные серверные разрешения.
4. Запрещённые денежные поля не маскируются интерфейсом, а полностью отсутствуют в ответе API.
5. Эта спецификация не меняет существующие данные. Новая схема начинается только после отдельного согласования шага 3.

## 2. Обязательные слои данных

Для каждого объекта одновременно существуют три разных слоя:

- **утверждённая база** — договорная выручка и разрешённая целевая себестоимость;
- **текущий прогноз** — действующие обязательства и оценка оставшихся затрат;
- **факт** — принятые затраты и фактическое движение денег.

Число из одного слоя нельзя использовать как замену числу из другого слоя. В частности, оплата не создаёт затрату, а аванс заказчика не создаёт прибыль.

## 3. Денежные представления и НДС

Для каждой операции, которая содержит НДС, различаются:

- `net_amount` — сумма без НДС; участвует в управленческой экономике и марже;
- `vat_amount` — сумма НДС; показывается отдельно и в маржу не входит;
- `gross_amount` — фактически предъявленная или оплаченная сумма с НДС.

Правила пересчёта:

```text
gross_amount = net_amount + vat_amount
net_amount = gross_amount / (1 + vat_rate / 100), если источник задан с НДС
vat_amount = gross_amount - net_amount
```

Правила округления:

- денежные суммы фиксируются с точностью до копейки;
- пересчёт из суммы с НДС выполняется на уровне строки;
- итог документа и объекта является суммой округлённых строк;
- для расчётов нельзя использовать двоичную арифметику `float` как источник окончательного денежного результата.

Управленческие показатели считаются по `net_amount`. Денежный поток показывает реально полученную или оплаченную `gross_amount`; рядом может выводиться её НДС-составляющая.

Версия 1 модели работает в рублях. Операция в другой валюте не включается в утверждённую экономику без зафиксированных валюты, курса и даты курса.

## 4. Зафиксированный словарь показателей

### 4.1. Договорная выручка

**Код показателя:** `contract_revenue`  
**Смысл:** утверждённая сумма, которую компания имеет право получить за согласованный объём объекта, без НДС.

```text
contract_revenue = утверждённая базовая выручка
                 + утверждённые изменения выручки
```

В показатель не входят:

- авансы и другие поступления денег;
- неподписанные дополнительные работы;
- черновики изменений;
- рыночные или закупочные цены;
- НДС.

Неподписанные дополнительные работы показываются отдельно как риск или потенциальная выручка и не увеличивают официальную прогнозную маржу.

### 4.2. Утверждённая целевая себестоимость

**Код показателя:** `target_cost`  
**Смысл:** разрешённая стоимость исполнения утверждённого объёма объекта, без НДС.

```text
target_cost = сумма действующих утверждённых бюджетных линий
            + утверждённый управленческий резерв
```

Изменение целевой себестоимости требует новой утверждённой версии или утверждённого изменения. Ручное редактирование итогового числа без причины и истории запрещается.

### 4.3. Принятые обязательства

**Коды показателей:** `committed_total`, `remaining_commitment`  
**Смысл:** стоимость утверждённых заказов, договоров и иных обязательств перед поставщиками и подрядчиками, без НДС.

```text
committed_total = сумма действующих утверждённых обязательств
remaining_commitment = сумма max(обязательство строки - принятый факт по строке, 0)
```

Выбранное предложение поставщика и черновик заказа обязательством не являются. Обязательство возникает только после утверждения заказа или договора уполномоченным пользователем.

Если принятый факт превысил обязательство, остаток обязательства по строке равен нулю, а превышение отражается как отдельное отклонение. Отрицательное обязательство не создаётся.

### 4.4. Начисленный факт затрат

**Код показателя:** `actual_cost`  
**Смысл:** стоимость фактически принятых или использованных ресурсов объекта независимо от оплаты, без НДС.

```text
actual_cost = утверждённые записи фактических затрат
            - утверждённые возвраты и сторно
```

Запись влияет на факт только после утверждения. Черновик, неподтверждённый прогресс, загруженный счёт или запланированный платёж в факт затрат не входят.

### 4.5. Денежный поток

**Коды показателей:** `cash_received`, `cash_paid`, `cash_balance`  
**Смысл:** реальное движение денег с учётом НДС.

```text
cash_received = фактически полученные входящие платежи
cash_paid = фактически совершённые исходящие платежи
cash_balance = cash_received - cash_paid
```

Операция входит в денежный факт только при статусе фактической оплаты и с фактической датой. Запланированные и одобренные, но не проведённые платежи относятся только к платёжному календарю.

`cash_balance` никогда не называется маржой или прибылью.

### 4.6. Прогноз затрат до завершения

**Код показателя:** `estimate_to_complete` (`ETC`)  
**Смысл:** ожидаемые будущие затраты, необходимые для завершения оставшегося объёма, без НДС.

```text
ETC = оставшаяся часть утверждённых обязательств
    + прогноз незаконтрактованного остатка
    + утверждённые прогнозные корректировки и риски
```

Для незаконтрактованного остатка источник цены выбирается по приоритету:

1. утверждённая цена действующего заказа — для уже законтрактованного объёма;
2. активное предложение поставщика — для незаконтрактованного объёма;
3. актуальная сохранённая цена AutoBot — только как прогнозный ориентир;
4. целевая цена утверждённого бюджета;
5. ручная прогнозная корректировка с обязательной причиной.

Источник более низкого приоритета не заменяет более высокий. У каждого компонента ETC сохраняются источник, дата расчёта и версия исходных данных.

### 4.7. Прогнозная итоговая себестоимость

**Код показателя:** `estimate_at_completion` (`EAC`)

```text
EAC = actual_cost + ETC
```

Полная сумма обязательства не прибавляется к факту. В ETC входит только ещё не принятая часть обязательства — это обязательное правило против двойного учёта.

### 4.8. Прогнозная маржа

**Коды показателей:** `forecast_margin`, `forecast_margin_percent`

```text
forecast_margin = contract_revenue - EAC
forecast_margin_percent = forecast_margin / contract_revenue * 100
```

Если `contract_revenue <= 0`, процент маржи не рассчитывается и возвращается как отсутствие значения, а не как `0%`.

Положительная маржа отображается зелёным, отрицательная — красным, нулевая — нейтральным цветом. Цвет не заменяет числовое значение и пояснение состава расчёта.

### 4.9. Отклонение от бюджета

**Код показателя:** `budget_variance`

```text
budget_variance = target_cost - EAC
```

Положительное значение означает прогнозную экономию, отрицательное — прогнозный перерасход.

## 5. Правила признания фактических затрат

| Событие | Когда признаётся факт затрат | Сумма без НДС | Что не является фактом |
|---|---|---|---|
| Материал доставлен прямо на объект | После подтверждённой приёмки фактического количества | Принятое количество × принятая цена | Заказ, ожидаемая поставка, счёт, предоплата |
| Материал поступил на центральный склад | Не является затратой конкретного объекта до выдачи или списания на него | — | Само поступление на склад |
| Материал выдан или списан на объект | После подтверждения выдачи/списания | Стоимость конкретной партии; если партия не определена — скользящая средневзвешенная стоимость на дату выдачи | Резерв и внутреннее перемещение без назначения объекту |
| Материал возвращён | После подтверждённого возврата | Отрицательная корректировка по стоимости исходной выдачи | Физическая пометка без количества и исходной партии |
| Работы субподрядчика | После принятия акта или подтверждённого объёма | Принятый объём × цена договора с учётом утверждённых изменений | Договор, заявка на оплату, неподписанный акт |
| Услуга или аренда | После принятия услуги/акта за период | Принятая сумма или объём × тариф | Счёт и плановый платёж |
| Собственный труд | После утверждения табеля и распределения на объект/работу | Часы × внутренняя ставка себестоимости | Выплата зарплаты и ручной процент готовности |
| Собственная техника | После утверждения машино-часов | Машино-часы × утверждённая внутренняя ставка | Перемещение техники и запись свободным текстом |
| Арендованная техника | После принятия смены/акта | Принятые часы или смены × договорный тариф | Бронь и предоплата |
| Логистика | После принятия доставки; распределяется по строкам по утверждённому правилу | Принятая стоимость доставки | Ожидаемая доставка |
| Накладные расходы | После утверждённого распределения за период | Распределённая сумма | Необъяснённая ручная корректировка |
| Малый ручной расход | После подтверждающего документа и утверждения пользователем с полномочием | Подтверждённая сумма | Запись без документа или причины |

Простой процент готовности работы сам по себе затрат не создаёт. Факт возникает из подтверждённых материалов, труда, техники, услуг и актов.

## 6. Правила единственности и корректировок

1. Одно хозяйственное событие может создать не более одной первичной записи фактических затрат.
2. У записи сохраняются `source_type` и `source_id`; повторная обработка того же источника не создаёт дубль.
3. Приёмка уменьшает оставшееся обязательство, но оплата его повторно не уменьшает.
4. Оплата меняет только денежный поток и расчёты с контрагентом.
5. Предоплата поставщику является исходящим денежным потоком, но не фактом затрат.
6. Возврат денег является денежным событием. Себестоимость меняется только отдельным возвратом, сторно или корректировочным документом.
7. Утверждённая запись не удаляется и не переписывается бесследно. Ошибка исправляется сторно и новой записью с причиной.
8. Изменение цены, количества, НДС, даты признания или распределения сохраняет автора, время, старое значение, новое значение и основание.

## 7. Матрица влияния событий на показатели

| Событие | Выручка | Целевая себестоимость | Обязательства | Факт затрат | Деньги | ETC/EAC |
|---|---:|---:|---:|---:|---:|---:|
| Утверждение базовой финансовой версии | Да | Да | Нет | Нет | Нет | Да |
| Выбор активного предложения | Нет | Нет | Нет | Нет | Нет | Да, только незаконтрактованный остаток |
| Утверждение заказа/договора | Нет | Нет | Да | Нет | Нет | Да |
| Приёмка материала или акта | Нет | Нет | Уменьшается остаток | Да | Нет | Да |
| Регистрация счёта | Нет | Нет | Нет | Нет | Нет | Нет; только платёжный календарь/сверка |
| Предоплата или оплата | Нет | Нет | Нет | Нет | Да | Нет |
| Утверждённое допсоглашение с заказчиком | Да | Только если отдельно изменён бюджет | Нет | Нет | Нет | Да |
| Сторно факта | Нет | Нет | Может восстановить остаток | Да, отрицательно | Нет | Да |
| Отмена непринятого остатка заказа | Нет | Нет | Да, уменьшение | Нет | Нет | Да |

## 8. Ролевой доступ к экономике

Полный экономический ответ включает договорную выручку, целевую себестоимость, обязательства, фактические затраты, ETC, EAC, отклонение и маржу.

- `main_admin`, `admin`, `director`: получают полный ответ и детализацию в пределах доступных объектов.
- `financier`, `accountant`: пока не получают эти поля.
- `foreman`, `purchaser` и остальные внутренние роли: не получают экономические суммы и производные показатели; сохраняются только отдельно разрешённые операционные действия.
- `customer`/`client`: не получают внутреннюю себестоимость, обязательства, закупочные цены, прогноз и маржу.

Проверка выполняется на backend до сериализации. Ответ для роли без доступа не должен содержать защищённые ключи даже со значением `null`, `0` или `hidden`.

Старые поля `budget`, `paid` и `spent` также считаются денежными и не должны обходить новую политику через общий ответ проекта.

## 9. Инварианты для будущих автоматических тестов

1. Оплата счёта меняет `cash_paid`, но не меняет `actual_cost`, `ETC`, `EAC` или маржу.
2. Предоплата не создаёт фактическую затрату.
3. Приёмка уменьшает `remaining_commitment` и увеличивает `actual_cost` на согласованную сумму без двойного изменения EAC.
4. Активное предложение меняет только прогноз незаконтрактованного остатка.
5. Черновой заказ не входит в обязательства.
6. Утверждённый заказ входит в обязательства, но не входит в фактические затраты.
7. Если выручка равна нулю, процент маржи отсутствует.
8. НДС не влияет на `target_cost`, `actual_cost`, `EAC` и `forecast_margin`, но входит в фактический денежный поток.
9. Повторная обработка одного источника не создаёт вторую затрату.
10. Ни один защищённый ключ не попадает в API для роли без экономического доступа.

## 10. Зафиксированная семантика существующих полей

### 10.1. `projects.budget`

Окончательная legacy-семантика поля:

> `projects.budget` — введённая ранее пользователем общая сумма с неустановленным экономическим назначением и неустановленным режимом НДС.

Поле **не считается автоматически**:

- договорной выручкой;
- целевой себестоимостью;
- лимитом затрат;
- прогнозом;
- фактом;
- денежным остатком.

До ручной классификации его пользовательское название — **«Legacy-бюджет (назначение не подтверждено)»**. Использование слова «утверждённый» для этого значения запрещается.

При будущей миграции исходное значение:

1. не изменяется и не обнуляется;
2. сохраняется как исходное значение для сверки;
3. получает контрольную сумму вместе с ID объекта и временем снимка;
4. не входит ни в один новый экономический показатель;
5. доступно только директору и администраторам;
6. после утверждения новой базы остаётся только историческим источником и не управляет расчётами.

Для каждого объекта директор или администратор должен выбрать ровно одну классификацию legacy-значения:

- `contract_revenue_candidate` — кандидат на договорную выручку;
- `target_cost_candidate` — кандидат на целевую себестоимость;
- `reference_only` — справочная сумма, не являющаяся финансовой базой;
- `ignore` — ошибочное или утратившее смысл значение.

Одна и та же legacy-сумма не переносится одновременно в выручку и себестоимость. Если бизнес-факт действительно требует одинаковых значений, они вводятся и утверждаются как две независимые величины с отдельными основаниями.

Классификация legacy-поля сама по себе ещё не утверждает новую финансовую базу. Пользователь обязан отдельно подтвердить сумму без НДС, НДС и источник-документ.

### 10.2. `projects.paid` и `projects.spent`

Эти поля имеют однозначную, но только кассовую семантику:

- `projects.paid` — сумма входящих `finance_entries` в статусе `paid`, то есть фактически полученные деньги с НДС;
- `projects.spent` — сумма исходящих `finance_entries` в статусе `paid`, то есть фактически оплаченные деньги с НДС.

Они не являются выручкой и себестоимостью. Разность `paid - spent` является legacy-денежным остатком и никогда не переносится в маржу.

Во время миграции эти поля продолжают пересчитываться для совместимости, но источником нового денежного потока остаются сами `finance_entries`, а не сохранённые итоги проекта.

### 10.3. `estimate_items.planned_price`

Окончательная legacy-семантика поля:

> `estimate_items.planned_price` — цена единицы, прочитанная или введённая в текущую смету; назначение цены и режим НДС определяются источником сметы, а не именем поля.

Само поле не доказывает, что цена является:

- ценой продажи заказчику;
- целевой себестоимостью;
- лимитом закупки;
- ценой поставщика;
- суммой без НДС или с НДС.

До классификации источника `planned_price`:

- продолжает отображаться в таблице «Цены и маржа» как legacy-цена сметы;
- может использоваться для существующего позиционного сравнения с предложением поставщика;
- не включается автоматически в договорную выручку или целевую себестоимость новой модели;
- не изменяется при выборе поставщика, создании заказа, приёмке или оплате.

Активное `supplier_offer` остаётся отдельной закупочной ценой. Его значение никогда не записывается в `planned_price`.

После появления версий сметы финансовая база будет получать снимок нормализованной цены без НДС. Последующие изменения живого `planned_price` не должны менять ранее утверждённую базу.

## 11. Классификация смет для миграции

### 11.1. Классы источника сметы

Каждая существующая смета классифицируется директором или администратором как один из вариантов:

- `customer_commercial` — коммерческая/договорная смета заказчику; строки являются кандидатами в договорную выручку;
- `internal_cost` — внутренняя ресурсная или затратная смета; строки являются кандидатами в целевую себестоимость;
- `mixed` — документ смешивает выручку и внутренние затраты; требуется классификация каждой строки или раздела;
- `unknown` — назначение доказать нельзя; строки не входят в новую финансовую базу.

Для `customer_commercial` и `internal_cost` дополнительно обязательно фиксируется режим цены:

- `net` — цена уже указана без НДС;
- `gross` — цена включает НДС, требуется ставка;
- `no_vat` — операция не облагается НДС;
- `unknown` — расчёт финансовой базы блокируется.

Если документ `mixed`, агрегированная сумма не переносится ни в выручку, ни в себестоимость. Каждая строка или однозначный раздел получает собственные назначение и режим НДС.

### 11.2. Статусы миграционной проверки

Для объекта используются следующие статусы:

- `unreviewed` — проверка не выполнялась;
- `ready_for_review` — автоматические проверки не нашли блокирующей аномалии, но человек ещё не подтвердил смысл;
- `blocked_anomaly` — обнаружено противоречие, перенос запрещён;
- `confirmed` — назначение, НДС, суммы и источники утверждены директором/администратором;
- `ignored` — legacy-данные сознательно исключены с указанием причины.

Статус `ready_for_review` никогда не превращается в `confirmed` автоматически.

### 11.3. Автоматические проверки до ручного решения

Для каждой сметы вычисляются:

- число строк и число строк с нулевой ценой;
- сумма `planned_qty × planned_price`;
- суммы по типу позиции и разделу;
- отношение суммы строк к `projects.budget`, если обе суммы положительны;
- строки с отрицательными количеством или ценой;
- строки с повреждённой/неизвестной единицей;
- подозрительные дубли;
- наличие исходного документа и его версии;
- наличие подтверждённого режима НДС.

Блокирующими считаются:

1. отрицательные количество или цена;
2. неположительный итог сметы при наличии строк;
3. отношение суммы сметы к `projects.budget` вне диапазона `0,80–1,20`, если обе суммы предполагаются сопоставимыми;
4. отдельная строка, сумма которой превышает legacy-бюджет объекта более чем в десять раз;
5. неизвестный режим НДС при попытке утвердить финансовую базу;
6. смешанная смета без построчной классификации;
7. отсутствие доказуемого источника для суммы, которую пытаются утвердить.

Нулевая цена, отсутствующая цена части строк, отличие в пределах 20%, повреждённая единица или вероятный дубль являются предупреждениями. Они не разрешают автоматический перенос и должны быть явно приняты или исправлены пользователем.

Диапазон `0,80–1,20` используется только как детектор аномалии. Попадание в него не доказывает, что `projects.budget` и сумма сметы имеют одинаковый экономический смысл.

### 11.4. Ручное подтверждение

Для создания утверждённой финансовой базы по существующему объекту директор или администратор отдельно подтверждает:

1. договорную выручку без НДС, сумму НДС и источник;
2. целевую себестоимость без НДС, резерв и источник;
3. назначение исходной сметы;
4. режим НДС исходных цен;
5. обработку нулевых, аномальных и смешанных строк;
6. дату, с которой база считается действующей;
7. комментарий о расхождении legacy-бюджета и суммы сметы.

До завершения всех обязательных подтверждений экономическое состояние объекта — `not_configured`. В интерфейсе показывается «Экономическая база не подтверждена», а официальная прогнозная маржа не рассчитывается.

## 12. Правила переноса по классу данных

| Legacy-источник | Допустимое действие после подтверждения | Запрещённое действие |
|---|---|---|
| `projects.budget` как договорная сумма | Создать кандидат договорной выручки, нормализовать НДС, приложить основание | Автоматически считать целевой себестоимостью |
| `projects.budget` как внутренний лимит | Создать кандидат целевой себестоимости, нормализовать НДС, приложить основание | Автоматически считать выручкой |
| Коммерческая смета | Создать строки базовой выручки по зафиксированной версии | Использовать те же строки как закупочную стоимость |
| Внутренняя затратная смета | Создать бюджетные линии целевой себестоимости | Использовать как договорную выручку |
| Смешанная смета | Разделить строки на выручку, себестоимость и исключённые | Перенести общий итог одной суммой |
| Смета неизвестного назначения | Оставить только историческим источником | Включать в маржу и EAC |
| Активное предложение поставщика | Использовать как источник прогноза незаконтрактованного остатка | Создавать утверждённое обязательство без заказа |
| Оплаченная `finance_entry` | Перенести как фактическое денежное движение | Автоматически создавать фактическую затрату |
| Неоплаченный счёт | Оставить в платёжном календаре и направить на сверку | Автоматически считать обязательством или фактом затрат |

## 14. Сохранность и воспроизводимость миграции

Будущая миграция должна соблюдать следующие требования:

1. Исходные `projects.budget`, `projects.paid`, `projects.spent`, `estimate_items.planned_qty` и `estimate_items.planned_price` не изменяются.
2. Для каждого миграционного кандидата сохраняются исходные значения, источник, версия/контрольная сумма и время снимка.
3. Любое решение о классификации содержит автора, дату, выбранный класс и комментарий.
4. Утверждённая финансовая база ссылается на конкретный снимок, а не на изменяемую текущую смету.
5. Повторный запуск миграции не создаёт дубли.
6. Отмена миграционного решения не удаляет историю и не восстанавливает показатели путём догадки.
7. До отдельного переключения старые экраны могут читать legacy-поля, но новые экономические расчёты их не используют.

## 15. Критерии завершения шагов 1–2

Шаги 1–2 считаются зафиксированными, если:

- каждое экономическое понятие имеет единственное определение и формулу;
- НДС отделён от управленческой маржи и остаётся в денежном потоке;
- определено событие признания каждого основного вида затрат;
- `projects.budget` и `estimate_items.planned_price` не получают неподтверждённого нового смысла;
- описаны статусы и блокирующие проверки миграции;
- для текущих объектов назначены предварительные статусы без изменения данных;
- зафиксированы правила серверной видимости;
- новые таблицы, миграции и расчётный код ещё не созданы.
