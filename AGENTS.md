# Работа с CRM PM.bi

## Контекст

Строительная CRM: Python 3.11, собственный HTTP-сервер, SQLite, HTML/CSS и обычный JavaScript. Точка входа — `backend/server.py`; страницы — `frontend/pages`, оболочка — `frontend/templates`, код интерфейса — `frontend/assets/js`, стили — `frontend/assets/css`.

Для рефакторинга прочитай актуальный этап в `CRM_REFACTOR_PLAN.md` и исходные результаты в `CRM_REFACTOR_VALIDATION.md`. Практический порядок работы и задания для GPT-6 Astra Medium/High находятся в `ASTRA_CRM_WORKFLOW.md`. При изменении экономики используй `PROJECT_ECONOMICS_SPEC.md`; для новых продуктовых сценариев — `RESEARCH_101_STWORKA_CRM.md`. Сверяй старые документы с текущим кодом и последними указаниями пользователя.

## Выполнение

- Доводи порученный объём до проверяемого результата. Обычные обратимые решения принимай самостоятельно в рамках запроса. Вопрос нужен, когда недоступный ответ существенно меняет продукт или последствия действия.
- В начале зафиксируй исходный diff и текущий этап. Сохраняй чужие и ранее выполненные изменения, включая незакоммиченные файлы.
- Делай связанные пакеты: один пользовательский сценарий или одна техническая граница с законченным поведением. Большую порученную работу продолжай такими пакетами; завершение одного пакета само по себе не завершает весь запрос.
- До правок определи наблюдаемый результат, существующие сценарии, которые должны сохраниться, и способ проверки. Для сложной логики кратко зафиксируй решение в плане; небольшой понятной правке отдельный план не нужен.
- Упрощай существующий механизм. Новая зависимость, слой или фреймворк должны решать конкретную задачу текущего этапа.
- После пакета обнови выполненное, результаты проверок, оставшиеся вопросы и следующий шаг в плане/отчёте. Отмечай завершение по доказанному поведению.
- После важных проверенных изменений делай коммит, отправляй его в Git и публикуй в production: пользователь явно поручил это 13 сентября 2026 года. Перед выпуском сверяй состояние сервера, сохраняй возможность отката и проверяй опубликованную версию. Повторное подтверждение обычного деплоя в рамках порученной работы не требуется; миграции рабочих данных требуют отдельного применимого плана.

## Интерфейс

- Цель — компактный рабочий интерфейс: существующие токены, спокойные поверхности, последовательные отступы, ясные подписи и одна главная кнопка на блок.
- Меняй правила в файле, который отвечает за компонент, удаляя заменённые стили. Избегай новых слоёв исправлений и наращивания `!important`.
- Сохраняй полезные данные, фильтры, действия и ограничения ролей при упрощении экрана.
- Изменения раскладки проверь в браузере на копии данных при 390, 768 и 1280 px. Проверяй переполнение, длинные подписи, доступность сохранения и затронутые состояния. Если размер или сценарий не проверен, укажи это.

## Логика и данные

- Сохраняй URL/API и поведение потребителей при выделении модулей; изменение контракта должно быть явной частью задачи.
- Сохраняй суммы в копейках, разделение базы/прогноза/факта/денежного движения, транзакции, ограничения проведённых записей и защиту от повторных операций.
- Проверяй доступ на сервере; запрещённые поля не должны попадать в API-ответ и DOM.
- Получай текущую бизнес-дату при выполнении операции через `business_time.today_iso`; не возвращай дату, зафиксированную при импорте.
- Для повторов и восстановления проверяй следующий запрос, повторное открытие и перезапуск, когда это относится к изменению.
- Тестовые записи, миграционные эксперименты и preview выполняй на изолированной БД. Миграция рабочих данных требует отдельного применимого плана; не исправляй обнаруженные связи удалением записей наугад.

## Проверки

В проекте нет общей команды `npm test`. Python-проверки запускаются из изолированной копии проекта с зависимостями:

```powershell
python -m unittest discover -s tests -p 'test_<затронутая_область>.py'
```

Frontend-наборы запускаются отдельно: `node tests/<имя>_frontend_tests.js`. Для router: `node --test tests/router_behavior_frontend_tests.js`. Полные команды и исходные падения — в `CRM_REFACTOR_VALIDATION.md`.

- Для изменения логики добавляй проверку значимого поведения. Для отступов/текста достаточно подходящей визуальной проверки и существующих затронутых тестов; не создавай тесты, повторяющие CSS-строки.
- Сначала запускай проверки затронутого участка; полный прогон нужен при общих изменениях, завершении крупного этапа или конкретном риске регрессии. Повторяй успешные проверки при изменении кода или появлении нового основания.
- Сравнивай новые падения с исходными по именам и причинам. Устаревшее ожидание меняй после определения актуального контракта, сохраняя полезное покрытие.
- Перед завершением отдельно просмотри diff на потерю требований, ошибки доступа, повторные операции и последствия для соседних сценариев. Такая самопроверка не является независимым ревью.
- В результате сообщи, что изменено, что проверено, какие проверки не прошли или не выполнялись. Не объявляй всю тестовую базу зелёной по одному успешному набору.
