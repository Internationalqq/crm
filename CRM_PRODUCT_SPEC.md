# PM.bi CRM — продуктовая спецификация

## Главная идея

CRM для строительной компании, где команда ведёт объект от сделки до завершения работ.

Главный экран должен отвечать на вопросы:

- что происходит на объекте сейчас;
- какой общий прогресс в процентах;
- какие работы выполнены, какие зависли;
- какие материалы уже куплены;
- какие материалы использованы;
- чего не хватает по смете;
- где перерасход;
- какие закупки нужно сделать срочно;
- что видит заказчик;
- что видит команда;
- кто за что отвечает.

## Роли

### Директор / админ

Видит всё:

- все объекты;
- финансы;
- прибыльность;
- закупочные цены;
- экономию на закупках;
- перерасход;
- роли пользователей;
- отчётность;
- AI-анализ;
- кредитный модуль.

Может:

- создавать пользователей;
- назначать роли;
- давать доступ заказчику;
- менять права;
- закрывать/открывать объекты;
- смотреть управленческие отчёты.

### Производитель работ / прораб

Ведёт объект в работе.

Видит:

- свои объекты;
- график производства работ;
- задачи;
- материалы по объекту;
- складские остатки по объекту;
- что закуплено;
- что использовано;
- чего не хватает;
- документы;
- чат команды.

Может:

- отмечать выполнение этапов;
- списывать материалы в работу;
- писать комментарии;
- заводить задачи;
- прикреплять фото/файлы;
- подтверждать фактическое выполнение.

Не обязательно видит:

- прибыльность проекта;
- маржу;
- внутреннюю управленческую аналитику директора.

### Закупщик

Отвечает за закупки и поставки.

Видит:

- заявки на закупку;
- материалы, которых не хватает;
- план поставок;
- склад;
- поставщиков;
- статусы оплат/доставок, если разрешено.

Может:

- создавать закупки;
- отмечать поступления;
- указывать фактическое количество и цену;
- менять статус поставки.

Ограничение:

- не должен видеть, насколько выгодно сделал закупку относительно внутреннего плана/маржи, если директор это скрыл;
- видит рабочую цену/задачу, но не полную финансовую картину.

### Заказчик

Имеет сильно ограниченный доступ.

Видит только свой объект:

- общий прогресс;
- график работ;
- текущий этап;
- фотоотчёты;
- документы, которые ему открыли;
- чат с командой;
- понятные статусы без внутренней кухни.

Не видит:

- другие объекты;
- склад;
- закупочные цены;
- внутренние задачи;
- маржу;
- прибыль;
- поставщиков, если это не разрешено;
- внутренний командный чат.

### Клиент / заказчик-руководитель

Если у заказчика несколько объектов, может видеть несколько своих объектов, но только в рамках своей компании.

## Авторизация и безопасность

CRM должна быть закрытой.

Нужны:

- вход по логину/паролю;
- роли пользователей;
- права доступа на уровне разделов;
- права доступа на уровне объекта;
- разные версии карточки объекта для команды и заказчика;
- невозможность открыть чужой объект прямой ссылкой;
- аудит действий: кто что изменил и когда.

Важно: статическая HTML-демка может только показывать интерфейс авторизации. Настоящая защита требует backend, базу данных и серверную проверку прав.

Текущий статус backend:

- добавлена страница входа `/login` на основе `frontend/templates/login.html`;
- добавлен frontend-клиент `frontend/assets/app.js`;
- добавлен backend `backend/server.py`;
- добавлена SQLite база `data/pmbi.sqlite3`, которая создаётся при первом запуске;
- пароли хешируются на сервере;
- сессии хранятся на сервере;
- HTML-страницы старой версии подключают auth-скрипт в `<head>`;
- backend проверяет сессию и роль до отдачи HTML-страниц и API-данных.
- экран объектов начал подтягивать список объектов и сводку материалов из backend API.
- frontend переведён со старой тяжёлой `deploy/copy` на нормальную структуру `frontend/templates`, `frontend/pages`, `frontend/assets`.

## Главные сущности

### Объект

Центр системы.

Поля:

- название;
- адрес;
- заказчик;
- договор;
- ответственный директор;
- производитель работ;
- закупщик;
- статус;
- даты начала/окончания;
- бюджет;
- плановая себестоимость;
- фактическая себестоимость;
- прогресс;
- риски.

### Смета

Загружается/сканируется внешним ботом.

CRM должна принимать результат сканирования:

- работы;
- материалы;
- количества;
- единицы измерения;
- плановые цены;
- этапы;
- привязка к объекту.

### Материалы

По каждому материалу нужно считать:

- нужно по смете;
- закуплено;
- поступило на склад;
- использовано;
- остаток;
- нехватка;
- перерасход.

Пример:

- по смете нужно 1000 труб;
- закуплено 800 труб;
- использовано 700 труб;
- остаток 100 труб;
- нехватка до сметы 200 труб;
- система пишет: “Нужно докупить 200 труб”.

### Склад

Нужен учёт:

- поступлений;
- списаний;
- остатков;
- материалов по объектам;
- общих материалов;
- перемещений между объектами;
- истории операций.

### График производства работ

Должен показывать:

- этапы;
- плановые даты;
- фактические даты;
- ответственных;
- прогресс по этапу;
- зависимость от материалов;
- просрочки;
- риски.

### Чаты

Нужно два уровня:

1. Внутренний чат команды по объекту.
2. Чат с заказчиком.

Заказчик не должен видеть внутренний командный чат.

## Самая важная функция

Система должна в реальном времени подбивать состояние объекта:

- сравнивать смету, закупки, склад и списания;
- показывать процент готовности;
- показывать нехватку материалов;
- показывать лишние закупки;
- показывать перерасход;
- подсказывать, что нужно сделать дальше;
- предупреждать о рисках по срокам и материалам.

Пример вывода:

- “По смете нужно 1000 труб. Куплено 800. Использовано 700. Остаток 100. Для закрытия сметы не хватает 200 труб.”
- “Этап ‘Монтаж труб’ выполнен на 70%, но материалов осталось только на 10% работ.”
- “Через 3 дня будет простой, если не заказать трубы.”

## AI-помощник

AI должен анализировать объект:

- смету;
- закупки;
- склад;
- списания;
- график работ;
- задачи;
- документы;
- переписку.

AI должен отвечать:

- что не хватает;
- где риск;
- какие этапы отстают;
- какие закупки нужны;
- где перерасход;
- что нужно сделать сегодня;
- что показать заказчику;
- какие документы/акты можно сформировать.

## Приоритет реализации

1. Авторизация и роли в интерфейсе.
2. Объект как центральная карточка.
3. Смета объекта.
4. Материалы: нужно / куплено / использовано / остаток / нехватка.
5. Склад и поступления.
6. График производства работ.
7. Чаты: команда и заказчик.
8. Заказчик: ограниченный личный кабинет.
9. Закупщик: заявки и поступления без лишней финансовой аналитики.
10. Директор: полная аналитика, финансы, прибыльность.
11. AI-анализ объекта.
12. Генерация актов и отчётности.
